# Frames: Polish, Local-First Media and Packaging Spec

Engineering spec for the Frames desktop app (Tauri 2 + Svelte, Rust core `frames-core`, MEGA S4 backend). Written as small, independent tasks so a weaker coding model (Gemini Flash) can execute each one correctly.

## How to use this spec

Give the agent **one task at a time**: paste the "Global rules" section plus the single task. Do not paste the whole document. Each task has files to touch, exact steps, a verification step and a stop condition.

### Recommended order

1. Phase 0 (recon), always first
2. Phase 1.2 and 1.3 (media pipeline and counts, the crucial part)
3. Phase 1.1, 1.4, 1.5 (visual polish), then Phase 4 (adaptive colour theming)
4. Phase 3 (icon)
5. Phase 2 (executables)

## Global rules (paste with every task)

- Do only the task you were given. Do not refactor, rename or reformat unrelated code.
- Touch only the files listed. If you need another file, stop and say why.
- Never invent file paths, function names or crate names. Use the names found in `docs/REPO_MAP.md` (created in Task 0.1).
- Make the smallest change that satisfies the acceptance check.
- After editing, run the verification commands. If anything fails, fix it once. If it still fails, stop and report the exact error. Do not keep guessing.
- Commit locally after each passing task: `git commit -am "task <id>: <title>"`. Do not push. No GitHub Actions.
- Reply with this report and nothing else:
  - Task ID
  - Files changed
  - Commands run and their result (pass or fail)
  - Anything you were unsure about

## Phase 1.2 (CRUCIAL): Local-first media, side thumbnails, web fallback

### Design in one paragraph

Every photo or video is one **asset row** in the SQLite index, keyed by album plus relative path. An asset can exist locally, remotely, or both. The UI never builds file or network URLs itself. It asks a custom protocol, `frames://thumb/<asset_id>/<size>` or `frames://photo/<asset_id>`, and Rust resolves the bytes in this order: **local original, then cached thumbnail or cached download, then S4 (fetch and cache)**. Thumbnails are generated by a background worker and never block the UI. Uploads run in their own queue at the same time.

### Task 1.2-a: Add columns to the asset table

**Files:** the database schema file and its migration code (from REPO\_MAP).

**Do:** add these columns if they do not already exist, with a migration that is safe to run twice:

- `local_path TEXT NULL` (absolute path of the original on this machine)
- `remote_key TEXT NULL` (the S4 object key)
- `thumb_state TEXT NOT NULL DEFAULT 'none'` (`none`, `queued`, `ready`, `failed`)
- `content_hash TEXT NULL`
- add a unique index on `(album_id, relative_path)`.

**Verify:** `cargo test -p frames-core` passes. Add one test that opens a fresh DB, runs migrations twice, and succeeds.

### Task 1.2-b: Local library root setting

**Files:** settings code in `frames-core`.

**Do:**

1. Add a setting `local_roots`: a list of absolute folder paths (for example the external drive folder containing album folders).
2. Add a Rust command `set_local_roots(paths: Vec<String>)` and `get_local_roots()`.
3. Each direct subfolder of a root is one album. The folder name is the album name. Match it to an existing album by name, case-insensitive.

**Verify:** a unit test creates a temp directory with two subfolders and checks that two album-to-folder matches are returned.

### Task 1.2-c: Scan local folders into asset rows

**Files:** new `frames-core/src/scan_local.rs` (or the nearest equivalent), plus module registration.

**Do:**

1. Walk each matched album folder (one level of recursion is fine, unless albums already support nesting).
2. Accept extensions: `jpg jpeg png heic webp gif tif tiff mp4 mov m4v`. Compare lowercase.
3. For each file, **upsert** an asset row by `(album_id, relative_path)`: set `local_path`. Never insert a second row for a file that already exists remotely. Update the existing row.
4. Do not read file contents here. Only metadata (size, modified time).
5. Run the scan on a background thread. Do not block the app start.

**Verify:** a test with a temp folder of 3 files scanned twice gives exactly 3 rows.

### Task 1.2-d: Thumbnail cache paths

**Files:** new `frames-core/src/thumbs.rs`.

**Do:** write only path helpers and a size enum:

- Sizes: `Small = 256`, `Large = 1024` (longest edge in pixels).
- Cache dir: the app cache directory plus `thumbs/<size>/`.
- File name: `<asset_id>.webp` (use `.jpg` if the repo has no webp encoder).
- Function `thumb_path(asset_id, size) -> PathBuf` and `thumb_exists(...) -> bool`.

**Verify:** a unit test checks the path ends with `thumbs/256/<id>.webp`.

### Task 1.2-e: Thumbnail generator for images

**Files:** `frames-core/src/thumbs.rs`.

**Do:**

1. Add `generate_image_thumb(src: &Path, asset_id, size)`. Use the `image` crate (add it if missing). Resize preserving aspect ratio, write to `thumb_path`. Write to a temp file, then rename, so half-written files never appear.
2. For HEIC, if the `image` crate cannot decode it, call the bundled `ffmpeg` to produce a JPEG frame instead.
3. Set `thumb_state = 'ready'` on success and `'failed'` on error. Never panic.

**Verify:** a test generates a thumbnail from a small PNG in the test fixtures and checks that the output exists and the longest edge is at most 256.

### Task 1.2-f: Thumbnail generator for videos

**Files:** `frames-core/src/thumbs.rs`.

**Do:** add `generate_video_thumb(src, asset_id, size)`. Run bundled ffmpeg: `ffmpeg -ss 1 -i <src> -frames:v 1 -vf scale=<size>:-2 <out>`. If the clip is shorter than 1 second, retry with `-ss 0`. Same temp-then-rename and state rules as 1.2-e.

**Verify:** compiles, and `cargo test -p frames-core` still passes. Video test is optional.

### Task 1.2-g: Background thumbnail worker

**Files:** new `frames-core/src/thumb_worker.rs`, plus app startup wiring.

**Do:**

1. A worker pool of **4** tasks (use `tokio::task::spawn_blocking` for the decoding).
2. Queue source: assets where `local_path IS NOT NULL AND thumb_state IN ('none','failed')`, newest album first.
3. Process visible-first: expose `prioritize(asset_ids)` so the UI can bump what is on screen.
4. After each thumbnail, emit a Tauri event `thumb-ready` with `{ asset_id }`.
5. Start the worker after the local scan finishes. It must never block the main thread or UI events.

**Verify:** app starts, `npm run tauri dev` shows no freeze, and thumbnail files appear in the cache dir.

### Task 1.2-h: The `frames://` protocol, thumbnails

**Files:** the Rust app setup file (where the Tauri builder is configured).

**Do:**

1. Register an asynchronous URI scheme protocol named `frames` using `register_asynchronous_uri_scheme_protocol`.
2. Handle path `/thumb/<asset_id>/<size>`. Look up the asset. If the thumbnail file exists, return its bytes with the right `Content-Type` and `Cache-Control: max-age=31536000`.
3. If it does not exist and the asset has `local_path`, generate it now (call the generator), then return it.
4. If the asset has no local file, call the remote fetch function (added in Task 1.2-l). Until that exists, return HTTP 404.
5. Add header `Access-Control-Allow-Origin: *` to every response.
6. In `tauri.conf.json`, add the `frames:` scheme (and on Windows `http://frames.localhost`) to the `img-src` and `media-src` CSP entries.

**Verify:** in the dev app, open the webview console and run `fetch('frames://thumb/<a real id>/256')`. On Windows use `http://frames.localhost/thumb/<id>/256`. The response status is 200.

### Task 1.2-i: One helper for the URL

**Files:** new `src/lib/media.ts`.

**Do:** export two functions, nothing else:

```ts
const isWindows = navigator.userAgent.includes('Windows');
const base = isWindows ? 'http://frames.localhost' : 'frames://localhost';
export const thumbUrl = (id: string, size: 256 | 1024 = 256) => `${base}/thumb/${id}/${size}`;
export const photoUrl = (id: string) => `${base}/photo/${id}`;
```

**Verify:** `npm run check` passes.

### Task 1.2-j: Use the helper in the grid

**Files:** the photo grid component and any thumbnail component it uses.

**Do:**

1. Replace every thumbnail `src` with `thumbUrl(asset.id)`. Remove any other URL building, base64 or `convertFileSrc` for thumbnails.
2. Add `loading="lazy"` and `decoding="async"` to each `<img>`.
3. Give each tile a fixed aspect-ratio box and a neutral placeholder background, so the layout does not jump.
4. Listen for the `thumb-ready` event. When it matches a tile, reload that image by appending `?v=<counter>` to the URL.
5. Tell the worker which assets are visible (`prioritize`) using an IntersectionObserver, debounced to 150 ms.

**Verify:** `npm run tauri dev`. Open an album that exists on disk. Thumbnails appear without network access (turn Wi-Fi off to confirm).

### Task 1.2-k: The `frames://` protocol, full photos and video

**Files:** the same Rust setup file as 1.2-h.

**Do:**

1. Handle path `/photo/<asset_id>`.
2. If `local_path` exists, stream the file. Support the HTTP `Range` header (needed for video seeking): return 206 with `Content-Range` when asked.
3. Else check the download cache (`<cache>/originals/<asset_id>`). If present, serve it the same way.
4. Else call the remote fetch function (Task 1.2-l). Until then, return 404.
5. Detect `Content-Type` from the extension.

**Verify:** in the viewer, a local photo opens at full resolution and a local video plays and seeks.

### Task 1.2-l: Remote fetch with caching

**Files:** the S4 access code in `frames-core`.

**Do:**

1. Add `fetch_remote_original(asset) -> PathBuf`: download `remote_key` into `<cache>/originals/<asset_id>` through a temp file, then rename. Return the path.
2. Add `fetch_remote_thumb(asset, size)`: if the library stores uploaded thumbnails in S4 at a thumbnail key, download that and save it to `thumb_path`. If no uploaded thumbnail exists, download the original and generate one.
3. A semaphore limits remote downloads to **6** at once. If two requests ask for the same asset, they share one download (a map of in-flight downloads).
4. Wire this into the protocol handlers from 1.2-h and 1.2-k, replacing the temporary 404.

**Verify:** with the local root unset, an album shows thumbnails fetched from S4. A second launch shows them instantly from the cache.

### Task 1.2-m: Sync remote album listings

**Files:** the S4 listing code.

**Do:**

1. On app start (after local scan), list objects for every album and **upsert** by `(album_id, relative_path)`: set `remote_key`. Never create a duplicate of a row that the local scan created.
2. Run in a background task. Emit event `album-synced` with `{ album_id }` when each album finishes.
3. Albums that exist only remotely appear as normal albums, loaded from the network when opened. Albums with a local folder keep using local files.

**Verify:** a remote-only album lists its photos. A local album that is also remote has no duplicate tiles.

### Task 1.2-n: Upload queue, concurrent with everything else

**Files:** the upload code.

**Do:**

1. A persistent table `upload_jobs(id, asset_id, state, error, updated_at)` with states `queued`, `running`, `done`, `failed`.
2. A separate worker with a concurrency limit of **3** uploads. It must not share a queue or lock with thumbnail work or remote downloads.
3. On success, set the asset's `remote_key` and mark the job `done`. On failure, mark `failed` and retry up to 3 times with growing delay (2 s, 10 s, 60 s).
4. Resume `queued` and `running` jobs at app start.
5. Emit `upload-progress` events with `{ job_id, state }`.

**Verify:** start an upload of a large file, then open a remote album at the same time. Both make progress. The UI stays responsive.

### Task 1.2-o: Small status indicator

**Files:** the sidebar footer component.

**Do:** show one line of text: "Uploading N", "Generating thumbnails N", or "Up to date". N comes from the events above. No new design, just text with the existing secondary text style.

**Verify:** the line changes while the workers run.

## Phase 1.4: Years / Months / All Photos selector

### Task 1.4-a: Find the control

**Files:** the top selector component (from REPO\_MAP).

**Do:** identify how the highlight is positioned now (fixed width, a percentage, CSS grid columns). Write one sentence in REPO\_MAP. No code change.

### Task 1.4-b: Measure each button and size the highlight

**Files:** the top selector component only.

**Do:** replace the highlight logic with measured values. Svelte 5 version (if the repo uses Svelte 4, use `let` and `$:` instead):

```svelte
<script lang="ts">
  import { tick, onMount } from 'svelte';
  let { items, selected = $bindable() } = $props();
  let buttons: HTMLButtonElement[] = $state([]);
  let left = $state(0);
  let width = $state(0);
  let ready = $state(false);

  async function measure() {
    await tick();
    const i = items.findIndex((it) => it.id === selected);
    const el = buttons[i];
    if (!el) return;
    left = el.offsetLeft;
    width = el.offsetWidth;
  }

  onMount(() => {
    document.fonts.ready.then(async () => { await measure(); ready = true; });
    const ro = new ResizeObserver(measure);
    buttons.forEach((b) => b && ro.observe(b));
    return () => ro.disconnect();
  });

  $effect(() => { selected; measure(); });
</script>

<div class="seg">
  <div class="pill" class:ready style="transform: translateX({left}px); width: {width}px"></div>
  {#each items as it, i}
    <button bind:this={buttons[i]} class:active={it.id === selected} onclick={() => (selected = it.id)}>{it.label}</button>
  {/each}
</div>
```

Rules for the CSS:

- `.seg { position: relative; display: inline-flex; padding: 3px; }`
- `.pill { position: absolute; top: 3px; bottom: 3px; left: 0; border-radius: 999px; }` (the existing glass look goes here)
- `.pill.ready { transition: transform 260ms cubic-bezier(.3,.7,.2,1), width 260ms cubic-bezier(.3,.7,.2,1); }` (no transition before `ready`, so it does not slide in on load)
- `.seg button { position: relative; z-index: 1; padding: 6px 16px; white-space: nowrap; }` and no fixed or equal widths on the buttons.

**Verify:** the highlight exactly covers "Years", "Months" and "All Photos" in turn, with the same padding on each side. Resize the window and change the system font size: still aligned.

## Phase 4: Adaptive colour theming

The Adaptive theme takes three colours from the photo being viewed and applies them to the background, the sidebar and the accent. Each album can instead keep one fixed palette, generated from its photos or chosen by hand.

### The three roles

| Role | Applied to | CSS variable | Rule |
| --- | --- | --- | --- |
| Background | main window background | `--adaptive-bg` | the photo's dominant colour, saturation capped at 0.35, lightness held in a narrow band |
| Sidebar | sidebar background | `--adaptive-sidebar` | a second, distinct colour; a little lighter or darker than the background |
| Accent | selection highlight, the Years / Months / All Photos pill, buttons, links | `--adaptive-accent` | the most vivid colour in the photo; falls back to `#0A84FF` for grey photos |

Tone: use whatever tone (light or dark) the Adaptive theme uses today. If it has none, use dark. Dark tone: background lightness 0.10 to 0.18, sidebar lightness = background + 0.04, accent lightness 0.45 to 0.65. Light tone: background 0.93 to 0.97, sidebar = background - 0.04, accent 0.40 to 0.55.

### The album setting

| Setting | Values | Default |
| --- | --- | --- |
| `theme_mode` | `dynamic` (a palette per photo) or `album` (one palette for every photo in the album) | `dynamic` |
| `theme_source` (only when mode is `album`) | `auto` (generated from the album's photos) or `manual` (three colours the user picks) | `auto` |
| manual colours | three hex values: background, sidebar, accent | none |

A photo always belongs to one album, so opening a photo from All Photos, Years or Months uses that album's setting.

### Task 4-c: Palette from one image

**Files:** new `frames-core/src/palette.rs`, plus module registration.

**Do:** write `extract_palette(thumb: &Path, tone: Tone) -> Palette` where `Palette { bg, sidebar, accent }` holds hex strings. Steps, in this order:

1. Open the 256 px thumbnail (Task 1.2-d). Shrink it to 64x64. Skip pixels with alpha below 128.
2. Reduce each pixel to 4 bits per channel (`r>>4, g>>4, b>>4`). Count pixels per bucket and keep the average real colour of each bucket.
3. Sort buckets by count, largest first. Call the largest `dominant`.
4. **Accent:** score each bucket as `sqrt(count) * saturation`, only for buckets with HSL lightness between 0.25 and 0.95. The best score wins. If the winner's saturation is below 0.35, use `#0A84FF`.
5. **Background:** `dominant`, with saturation capped at 0.35 and lightness moved into the tone's band (table above).
6. **Sidebar:** the next bucket whose hue differs from the background by at least 20 degrees, with lightness set to the tone's sidebar rule. If none, use the background with the sidebar lightness rule applied.
7. Call `normalise_roles(bg, sidebar, accent, tone)` (below).

Also write `normalise_roles`, used by every palette path:

1. If two of the three colours are closer than 40 (straight RGB distance), move the sidebar lightness by 0.05 in the tone's direction until they are 40 apart (at most 10 steps).
2. Accent against background must have contrast at least 3.0. If not, change the accent lightness by 0.05 per step, up to 10 steps.
3. Also return two text colours, `on_bg` and `on_sidebar`, each either `#FFFFFF` or `#111111`, whichever gives contrast of at least 4.5 with its surface.

The function must be deterministic: the same image gives the same palette.

**Verify:** tests with generated images: a solid red image gives an accent near red; a half blue, half orange image gives three different colours; a grey image gives accent `#0A84FF`; a white image and a black image both give text contrast of at least 4.5. `cargo test -p frames-core` passes.

### Task 4-f: Generate the album palette automatically

**Files:** new `frames-core/src/album_palette.rs`, plus a command `regenerate_album_palette(album_id)`.

**Do:**

1. Take the album's assets sorted by date. Pick up to 60, evenly spaced. For each, get its palette (Task 4-d); skip the ones without a thumbnail.
2. Split the hue circle into 12 buckets of 30 degrees. Collect all the picked photos' accent colours and put each in a bucket by hue. Ignore accents with saturation below 0.35.
3. The bucket with the most members wins. The album accent is the average of its members. If no bucket has members, use `#0A84FF`.
4. The album background is the average of the background colours of the photos in the winning bucket (all photos if the bucket has fewer than 3). The album sidebar is the average of their sidebar colours.
5. Pass the three results through `normalise_roles` (Task 4-c).
6. Save to the `auto_*` columns. Run on a background thread. Emit event `album-palette-ready` with `{ album_id }`.
7. Run it when the user turns on `album` mode with `auto`, when the user presses Regenerate, and when an album's file count changes by more than 10 percent after a sync.
